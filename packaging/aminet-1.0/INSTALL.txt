CopperSFS 1.0 - installation and runtime settings
================================================

EXPERIMENTAL. Use disposable existing SFS\0 volumes and independent backups.
The handler requires a 68020 or newer CPU and AmigaOS 2.04+. CopperSFSCtrl
uses 68000 instructions, but does not change the handler CPU requirement.
Testing used Kickstart 3.1. Physical devices and other ROMs remain unqualified.

Installation
------------
1. Extract CopperSFS.lha keeping drawer paths. It uses standard level-0
   stored (-lh0-) entries. Verify the outer archive SHA-256 and internal
   SHA256SUMS.txt with a host SHA-256 tool; these are not AmigaDOS Sum files.
2. Finish work with the current handler, close files and stop applications.
   Complete a checked filesystem ACTION_FLUSH or successful clean Inhibit.
   With a compatible CopperSFS already running, use:
     CopperSFSCtrl SFS0: FLUSH
   The command returns 0 on success, 20 on failure. Closing files,
   dos.library/Flush(file), waiting or an idle light do not confirm durability.
3. Recover any interrupted CSUN transaction with CopperSFS on a writable
   device before switching handlers. Preserve the image if recovery fails.
4. Boot from a separate volume with the test volume unmounted. Back up the
   old handler. Replacing a file does not replace a running handler. Never
   mount a partition simultaneously through two handlers. Install:
     Copy CopperSFS L:CopperSFS
     Copy CopperSFSCtrl C:CopperSFSCtrl
5. Copy SFS0.mount.example to DEVS:DOSDrivers/SFS0 on OS 2.1+, or create an
   equivalent DEVS:MountList entry on OS 2.04. Replace EVERY CHANGE_ME with
   the existing partition's exact device, unit and geometry. Check Mask,
   MaxTransfer, SizeBlock, Reserved and SectorsPerBlock. SizeBlock counts
   longwords; 512-byte blocks normally use 128. Do not copy test geometry.
   FileSystem = L:CopperSFS, DosType = 0x53465300 and Forceload = 1 select
   this handler. Do not format the partition.
6. Mount SFS0:, List SFS0:, then write/read a small test file. Run a checked
   FLUSH, reboot from the separate boot volume, remount and verify it again.

One handler, per-volume runtime options
--------------------------------------
  CopperSFSCtrl SFS0: INFO
  CopperSFSCtrl SFS0: DATACACHE 128K
  CopperSFSCtrl SFS0: DATACACHE 512K
  CopperSFSCtrl SFS0: DATACACHE OFF
  CopperSFSCtrl SFS0: WRITEMODE STRICT
  CopperSFSCtrl SFS0: WRITEMODE BUFFERED
  CopperSFSCtrl SFS0: FLUSH

Choose one operation per command. Omitting an operation means INFO. Options
apply to the named mounted volume. They are not saved on disk. To restore
settings at boot, put the desired commands in S:User-Startup after mounting
that volume and before starting applications that use it. Check failures.

INFO reports requested and actual data capacity, pool allocation, metadata
buffer count, write-buffer and physical-queue allocations, active write mode,
pending writes and pending recovery. These are not total process memory.
The version tag records startup defaults; INFO shows the current settings.
Use Version L:CopperSFS FILE FULL for executable identification.

The default is buffered writes with a 256 KiB clean-data cache. At mount,
allocation failure halves the cache until a pool fits, eventually using no
clean cache. Write-buffer or timer allocation failure selects strict writes.

Explicit DATACACHE changes require the exact requested capacity; failure
leaves the old cache intact. Zero or OFF disables it. Otherwise choose 4 to
256 pages in powers of two, each page containing 16 filesystem blocks. With
512-byte blocks: 32K, 64K, 128K, 256K, 512K, 1M or 2M. Bare bytes and K/M
suffixes are accepted. Growth temporarily needs both the old and new pools.
Resizing discards only clean cached data; pending writes and file positions
are retained. It issues no disk I/O. ADDBUFFERS controls metadata buffers,
and does not resize this clean-data pool.

Data capacity (512-byte blocks)   Pool allocation
  disabled                                  0
  128 KiB                             131,360
  256 KiB                             262,688
  512 KiB                             525,344
  2 MiB                             2,101,280

The default handler measured 585,480 bytes loaded and mounted in the test
profile. This includes code, process, stack and mount buffers. Each volume
has its own allocations; open files need more RAM. The buffered write buffer
uses 50,256 bytes and physical phase queue 69,408 bytes at 512-byte blocks.

An initial sequential pass does not populate the clean cache. A reread or
seek on the same open handle enables admission; a later pass can hit.
Reopening alone does not seed an empty pool. Reads of at least 8 KiB from
files larger than the actual pool bypass it. Writes, recovery and handoff
invalidate clean data. The cache adds no speculative disk reads or dirty data.

Write modes and recovery
------------------------
Changing write mode completes a checkpoint before publishing the new mode.
A failed checkpoint retains the old mode and reports failure; pending
recovery must be resolved before another mode change. Enabling buffering
also needs a write buffer and timer. Allocation failure keeps strict mode.
Selecting the already active mode is a no-op; use FLUSH for a checkpoint.
Open handles and file positions remain valid during configuration changes.

Buffered writes checkpoint five seconds after the first pending change,
at buffer pressure, on successful filesystem ACTION_FLUSH, or before
successful clean inhibit. Pending changes are visible to readers. Recent
unflushed changes may be lost in a crash. Strict mode commits each successful
mutation before replying, but does not make several application operations
atomic. Both modes use the same journal and ordered flush barriers.

The handler uses classic 32-bit DOS file sizes and seek positions. Device
access beyond 4 GiB requires TD64 reads and writes. NSD is not supported.
Native large-device use remains unqualified. See VALIDATION.txt for coverage.
