# Original SFS implementation study

Original SFS avoids allocation and extent edits when overwriting existing data; our whole-write atomic design uses replacement data and metadata. This explains its cheaper setup, boundary and commit operations. Qualified v77, now integrated as v78, offsets that cost with cheaper ordinary continuations and reaches measured overwrite throughput parity. The TRST encoder is a small part of the measured cost. This investigation identified the original's inline journal shortcut and the value of retaining validated file/run state. Both have informed subsequently integrated and qualified changes. The comparisons below separate throughput from setup and tail latency.

Earlier work concentrated too heavily on our generated code after establishing that original SFS overwrites in place. That left useful differences in its cache and commit paths insufficiently investigated. This study compares the published SFS-derived C implementation with disassembly, actual calls and sector writes from the exact SFS 1.279 binary used in our benchmarks.

The initial [comparison receipt](../artifacts/native-trst-original-study/comparison.json) contains input hashes, call counts, timings, source verification and sector evidence. That investigation used the [qualified preflight build](native-trst-preflight.md), SHA-256 `698DBD56AF82F99B0F99B2E108D4056515179290215E0248664B238CB62944DF`. The study itself changed no production code; later integrations are identified separately.

Subsequent implementation: the [inline TRST writer](native-trst-inline.md) adopts the confirmed single-sector shortcut and has passed crash recovery and original-handler compatibility qualification. Its report includes the benchmark gains and latency tradeoffs.

It takes 4,606,154 cycles versus 2,959,553 for original. The three remaining generic packets account for **51.14% of the remaining excess cycles**. Two still split an extent, remove its temporary prefix and insert the replacement; the third crosses a source bitmap boundary. These are the next concrete targets. The codec remains about **1%** of total cycles.

The older published [extension path](https://github.com/aros-development-team/AROS/blob/918572d1d0318b4b5024c564bdcaf9fafa6b2798/rom/filesys/SFS/FS/filesystemmain.c#L4124) starts allocation at the end of the current extent, or at a retained cursor. This supports the locality lesson behind our forward search. It does not establish the exact allocation-search policy of the 1.279 binary, and original SFS still avoids allocation altogether in the measured overwrite workload.

## Deferred metadata checkpoint

The [deferred metadata implementation](native-trst-deferred.md) introduced a bounded accepted run and materializes its extent/bitmap edits before reads, mutations or commit. It preserves whole-Write atomicity, pending-read visibility, failed-Write rollback and the 192 KiB staging cap. Its qualified 160,204-byte native HUNK has SHA-256 `DAE8EBD105D7C00935E4CB140F7645D58F932DEA0A498CBCDFD4503BA3FB8741`; the live build at that checkpoint reproduced it exactly.

The five-trial benchmark improves overwrite throughput by **13.79%**, reaching **59.73% of original SFS**. Append throughput regresses by 1.82–2.41% from the preceding build but still reaches 103.90–126.71% of original. Worst-Write and checkpoint latency increase. These tradeoffs, renewed crash tests and original-handler compatibility results are documented in the implementation report; the overall parity goal is still unmet.

A [new packet analysis](../artifacts/native-trst-deferred/original-comparison-v4.json) compares this build's diagnostic with the saved original/pending-entry diagnostics below. It takes 4,954,893 cycles versus 2,959,553 for original. Typical deferred Writes now take 23,926 cycles, down from 30,366, versus original's 20,046 at the same indices. Five generic allocation/relocation Writes account for **61.18% of the remaining excess cycles**; three proof-building Writes account for another 8.69%. Encoder instructions are **0.94%** of the total. The next substantial target is these setup/boundary transitions and repeated bitmap accounting.

## Pending-entry comparison before deferred metadata

Two diagnostics compare the exact SFS 1.279 binary with the then-qualified [pending-entry handler](native-trst-pending.md), SHA-256 `B6184E8D7A4CC56AC512BF0652803F937AA8FB682FAF49331C8D2BBE8FD5ACB4`. Both write the same 1 MiB through 128 8 KiB overwrite packets on the same emulated 68020 and fixture. Both pass independent deep image checking and exact-byte extraction. The [receipt](../artifacts/native-trst-original-current/comparison.json) verifies both binary and map hashes, all 52 reference-source hashes, packet classifications and test results. Its [analysis script](../artifacts/native-trst-original-current/analyze.py) reproduces the partition below.

The original again executes 128 extent lookups, zero file-extension/allocation calls and one metadata compression over the complete interval. It retains file size, protection and extent state between requests. The older published source shows explicit updates or invalidation when protection, file size or extent placement changes. This is the useful design lesson: retain state whose lifetime is defined, rather than repeatedly retrieving unchanged metadata. The original's in-place payload writes do not provide our required whole-Write atomicity.

The pending-entry handler takes 5,642,264 guest cycles versus 2,959,553 for original SFS. **97.19% of that difference occurs inside the Write packet intervals.** Their disjoint partition is:

| Our path taken at those packet indices | Packets | Our total cycles | Original total cycles at the same indices | Share of overall excess |
| --- | ---: | ---: | ---: | ---: |
| Existing pending continuation | 120 | 3,837,434 | 2,548,380 | 48.05% |
| Generic relocation/allocation | 5 | 1,266,245 | 104,975 | 43.29% |
| Continuation proof construction | 3 | 217,068 | 60,138 | 5.85% |
| Other work and final checkpoint | — | 321,517 | 246,060 | 2.81% |

Typical pending packets take 30,366 cycles versus 20,046 at the same original packet indices. However, optimizing those packets alone misses roughly half the excess: five generic transitions and three proof-building packets also need attention. The generic packets are zero-based indices 0, 1, 22, 63 and 64; proof construction occurs at 2, 23 and 65. The slowest packet, index 63, enters relocation, two free-run scans, an arena clone and touched-bitmap free-count work. These call observations identify its work, not the precise contribution of each nested routine.

No `CopyBlock` call occurs inside the 120 pending packets. There are 47 such calls in the five generic packets. Both writers already publish one inline TRST page and use four device flushes. Original writes 2,051 sectors in 131 requests; ours writes 2,056 sectors in 136 requests, plus eight sector reads in one request. The five extra writes are home metadata for replacement allocation/mapping. The TRST codec planner consumes 46,791 exclusive instruction cycles, **0.83%** of our total. Neither encoding nor payload copying explains the recurring continuation cost.

That comparison motivated the bounded retained run described above, amortizing extent and bitmap work across consecutive accepted Writes. Cheaper generic allocation/proof transitions remain to be implemented. Pending reads and other metadata operations must observe every accepted Write; a later failed transfer must preserve all earlier accepted Writes. The 192 KiB staging cap, delayed durability and CSUN recovery remain unchanged. Copying the original's in-place data overwrite would discard a required guarantee.

These were diagnostic runs, not a new acceptance benchmark or crash qualification. At that checkpoint the five-trial benchmark reached 129.84% of original for 8 KiB append, 105.83% for 64 KiB append, and 52.49% for overwrite. That diagnostic follow-up changed no writer code. Dynamic function times are not added: parent/child intervals overlap, and the original also executes device work on a separate task. Packet intervals and the final checkpoint provide the comparable end-to-end partition.

## What the original does

The published [file-write implementation](https://github.com/aros-development-team/AROS/blob/918572d1d0318b4b5024c564bdcaf9fafa6b2798/rom/filesys/SFS/FS/filesystemmain.c#L4992) keeps a current extent key and offset in the file lock. It extends allocation only when necessary and edits the object size only when the size changes. Aligned full blocks go to the bulk write path. This is an older SFS-derived source reference, not the matching source for 1.279.

The measured 1.279 binary confirms those branches. Its file-write entry is code-hunk offset `0x92C8`; the unchanged-size branch at `0x9406` skips the metadata edit, the extent lookup is at `0x94BA`, and the bulk write call is at `0x9696`. It still looks up the current extent on each Write; it does not eliminate every tree lookup. See the [disassembly](../artifacts/native-trst-original-study/original-write-file-full.asm).

Actual completed calls over the three original-handler workloads are:

| Operation in SFS 1.279 | 128 × 8 KiB overwrite | 128 × 8 KiB append | 16 × 64 KiB append |
| --- | ---: | ---: | ---: |
| File-write entry | 128 | 128 | 16 |
| Extend-file path | 0 | 128 | 16 |
| Allocation path called by extension | 0 | 128 | 16 |
| Extent-tree lookup | 128 | 512 | 64 |
| Metadata-store entry | 0 | 515 | 67 |
| Metadata difference compression | 1 | 518 | 69 |

Counts cover the complete measured interval, including Close and the checkpoint. Zero calls to the metadata-store entry does not mean zero metadata changes: the overwrite interval includes one compressed object-block update through another entry. The compressor is at `0x14808`; the checksum setter is at `0xB48A`. Disassembly distinguishes them rather than assigning names to the old 256-byte profile buckets.

The published [metadata cache](https://github.com/aros-development-team/AROS/blob/918572d1d0318b4b5024c564bdcaf9fafa6b2798/rom/filesys/SFS/FS/cachebuffers.c#L335) preserves an original image when first modifying a clean buffer and reuses an already modified buffer. Its [transaction code](https://github.com/aros-development-team/AROS/blob/918572d1d0318b4b5024c564bdcaf9fafa6b2798/rom/filesys/SFS/FS/transactions.c#L380) retains the newest operation for a block when transactions are combined. End-of-operation handling starts the delayed-commit timer and can flush under transaction-space pressure. The exact 1.279 end-transaction routine has additional checks, so the older source's precise threshold is not assumed to apply to it.

At the initial study baseline, our continuation path already edited owned arena images in place after successful unpublished data I/O. It did not clone the whole arena for every Write. That overwrite had 125 continuation attempts, five generic write-path calls and four arena clones. The remaining issue included repeated validation, metadata access and updates, plus the expensive generic transitions.

## Cache behavior

Original SFS has separate metadata buffers and an I/O cache. The [published I/O path](https://github.com/aros-development-team/AROS/blob/918572d1d0318b4b5024c564bdcaf9fafa6b2798/rom/filesys/SFS/FS/cachedio.c#L814) checks overlapping cache lines, uses copyback for small requests, and sends larger requests through to the device.

RAM snapshots from 1.279 confirm **eight 8 KiB I/O cache lines**, with copyback enabled and 512-byte filesystem blocks. The bulk dispatch at `0xF978` takes the direct path for the measured 8 KiB payloads. All 128 overwrite payloads are aligned to an 8 KiB line, so the overlap loop checks one line per Write. The fixture's appends are not aligned to those lines: they span two lines per 8 KiB Write or nine per 64 KiB Write.

Our native cache invalidator checks 16 block-hash buckets for each 8 KiB payload. The separate baseline cache trace found no matching cached blocks in any of the 129 invalidations. This is avoidable work, but its exclusive instruction cost is about 228,000 cycles, only 3.8% of the total. A cache change alone cannot remove a roughly three-million-cycle gap. The experimental cache-gap candidate remains [unintegrated and unqualified](../artifacts/native-trst-cache-envelope/parked.json).

## The original's journal shortcut

The exact binary contains a path absent from the inspected older C source. When the complete transaction fits in one block and its single-sector condition holds, `savetransaction` places TRST directly at **root container + 2**. In this fixture that is block 5. `flushtransaction` sees that location and skips the separate TRFA write. See [transaction storage](../artifacts/native-trst-original-study/original-savetransaction.asm) at `0x15AB4`–`0x15B8C` and [commit dispatch](../artifacts/native-trst-original-study/original-flushtransaction.asm) at `0x16A7C`–`0x16A86`.

The initial study's overwrite sector trace was:

| Phase | Original SFS 1.279 | Native TRST preflight build |
| --- | --- | --- |
| Payload | 2,048 sectors, in place | 2,048 sectors, unpublished replacement space |
| Journal publication | Flush data; write TRST to block 5; flush | Write external TRST at block 3,646; flush; write TRFA at block 5; flush |
| Home metadata | One object block; flush | Six metadata blocks; flush |
| Completion | TROK at block 5; flush | TROK at block 5; flush |
| Total | 2,051 sector writes, 131 write requests, four flushes | 2,057 sector writes, 137 write requests, four flushes |

Thus the six extra native sector writes are five extra home metadata images for replacement allocation/mapping, plus TRFA. Native TRST also reads eight sectors in one request; the original reads none during this interval. Both write one 512-byte TRST page.

Original SFS also combines nearby dirty metadata into device requests. In the append trace, one request writes blocks 3–8, including the already written TRST block 5. The benchmark's `TrstPages: 2` therefore counts two physical TRST writes to the **same block**, not a two-page journal chain. The [sector receipts](../artifacts/native-trst-original-study/comparison.json) make this distinction explicit.

Our classic recovery path already recognized TRST directly in the marker block. The subsequent inline writer adopted that behavior for the observed 512-byte case and passed crash cuts, interrupted replay and original-handler handoff tests. Replacement data must be flushed before writing that TRST block, because this write itself publishes the transaction. Larger journals retain the external-page/TRFA path.

## Cost and next work

The paired v3 diagnostic measures **2,959,583 guest cycles** for original overwrite and **5,973,853** for native TRST. Within those intervals, the original file-write routine accounts for 911,996 elapsed cycles; our `WriteSmartFile` accounts for 4,340,094. Our continuation handling accounts for 2,284,040 elapsed cycles. Parent and child timings overlap and must not be added.

The codec planner's exclusive instruction cost is **46,660 cycles, about 0.8%**. The entire native commit call takes about 222,000 elapsed cycles. This rules out journal encoding or the extra publication write as the main cause of the remaining overwrite gap in this CPU-focused benchmark. The previous acceptance benchmark remains authoritative for throughput: native TRST wins both tested append sizes, while overwrite reaches 49.5% of original SFS throughput.

The initial study proposed adopting the original small-journal publication path and reducing repeated work in the atomic overwrite continuation. The first is now integrated; the latter remains the main target. It needs an explicit account of which state can safely remain valid across Writes. A bounded run descriptor or deferred metadata edits must still serve pending reads, preserve accepted Writes after a later failure, and invalidate on extent, allocation, media or arena changes. Removing private-record checks or copying the original's in-place overwrite behavior would not meet the existing requirements.

The **192 KiB staging cap, whole-write atomicity, buffered delayed durability and CSUN recovery remain requirements**. The performance goal remains unmet.

## Evidence limits

The original HUNK is 97,984 bytes with SHA-256 `C7DD174131035A0F5845BE1076FB5C55642F6AA2125D4B5D8C029B141DCC8205`, identifying SmartFilesystem 1.279 dated 23 December 2007. The source reference pins 52 files at AROS commit `918572d1d0318b4b5024c564bdcaf9fafa6b2798`; all file hashes were checked. Matching 1.279 C source was not located. Claims specific to that version above come from the binary and runtime observations.

The diagnostic observes actual JSR/BSR calls and return stack slots, with separate stacks for each Exec task. Original SFS executes observed calls on three tasks. At measurement end its three outstanding frames are blocked Wait/WaitPort calls; native TRST has one blocked WaitPort frame. There are no invalid call observations or outstanding internal handler frames. Earlier diagnostic v1/v2 timings incorrectly shared one stack across tasks and are excluded.

Dynamic call times include scheduling and interrupts. Exclusive method rows count executed instruction cycles. With dynamic observation disabled, original overwrite reproduces the entire trial exactly. Native overwrite retains identical handler instruction counts, I/O and sampled memory, with a 0.024% cycle difference and 98 additional outside-handler instructions. This small variation is recorded in the [observer controls](../artifacts/native-trst-original-study/observer-controls.json), not treated as an optimization.

Seven task-aware profiles and two observer-control runs pass independent deep image and exact-byte checks. Diagnostic v4 additionally saves sector events and actual buffer headers. The frozen diagnostic builds pass; they add no guest instructions or emulator changes. These runs investigate the already-qualified writer. They do not constitute new crash qualification, physical storage testing or a new acceptance benchmark.
